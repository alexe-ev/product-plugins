Ключевые наблюдения

Скилл устойчив на независимых данных

Обе итерации показали 100% для with_skill. Первая итерация использовала примеры из самого скилла (кейс онбординга iOS), вторая — совершенно новые домены (финтех, B2B SaaS, generic A/B). Разницы нет. Это признак реального обобщения, а не запоминания примеров.

Light context — главная уязвимость базовой модели

Без скилла при неполном контексте модель уверенно даёт конкретные цифры ("конверсия 3–8%", "типичный SaaS target") без каких-либо provisional-маркеров. Это создаёт риск: команда может воспринять эти цифры как рекомендацию, а не гипотезу для проверки. Этот паттерн воспроизводится в обеих итерациях стабильно.

Rich context — скилл не нужен, и это нормально

Когда пользователь даёт чёткую гипотезу, бизнес-цель и контекст — базовая модель справляется самостоятельно. Итерация 2 показала 100%/100% для rich-context. Скилл не мешает, но и не добавляет ценности. Потенциальный вывод: можно рассмотреть условный триггер скилла по наличию гипотезы в запросе.

Overhead оправдан для light/poor context

Скилл добавляет в среднем +8 секунд и +3 000 токенов на запрос. Для rich-context это лишние расходы без выгоды. Для light-context — это цена за +67pp качества, что более чем оправдано перед запуском эксперимента с возможными неверными метриками.

Провальный паттерн без скилла воспроизводим

Провал без скилла на light-context (33%) наблюдается в обеих итерациях при разных промптах. Это сильный сигнал: мы видим системное поведение модели, а не случайный результат одного запуска. Одинаковые assertion failures: отсутствие provisional-маркеров, уверенные цифры без уточнения дефиниций.

Слабое место в evals: rich-context assertions

Rich-context assertions не дифференцируют скилл и baseline — обе конфигурации 6/6 в iter2. Либо assertions слишком лёгкие, либо rich-context не является зоной ценности скилла. Рекомендация: добавить более жёсткие assertions — например, проверку наличия explicit reasoning об альтернативных метриках которые были отклонены.

Рекомендации

01
Расширить набор light-context кейсов высокий приоритет

Light-context — это главная зона ценности скилла и самый воспроизводимый провал без него. Текущий набор — 2 промпта из 6. Нужно добавить ещё 3–5 вариантов разных доменов и уровней «неполноты» (mobile app, marketplace, внутренний инструмент, data product). Это укрепит уверенность в результате и поможет выявить edge cases.

02
Усилить assertions для rich-context средний приоритет

Текущие assertions для богатого контекста не отличают скилл от baseline. Добавить: явную проверку наличия reasoning о почему другие метрики были отклонены, проверку структуры (primary/secondary/guardrail — все три явно поименованы), и проверку что minimum meaningful effect не просто помечен provisional, а сопровождён объяснением как его определить.

03
Проверить explicit provisional-язык в SKILL.md средний приоритет

With_skill не показал ни одного провала за всё тестирование. Тем не менее разрыв с baseline на assertion «explicitly labels choices as provisional» — самый стабильный сигнал: именно здесь baseline заваливается в обеих итерациях. Стоит убедиться, что SKILL.md явно инструктирует использовать маркеры типа IF/PROVISIONAL/CONDITIONAL в тексте, а не только структурировать условно — это делает скилл устойчивым к изменениям базовой модели в будущем.

04
Добавить тест на «ложноположительный уверенный ответ» средний приоритет

Главная проблема базовой модели — не ошибка структуры, а уверенный тон без оснований. Стоит добавить assertion который проверяет отсутствие конкретных числовых threshold'ов без явного предисловия «to be confirmed» или аналогичного. Это сделает eval более дискриминирующим.

05
Запустить оптимизацию описания скилла (run_loop.py) низкий приоритет

После расширения тест-кейсов — запустить скрипт оптимизации триггера. Цель: убедиться, что скилл активируется именно при light- и poor-context запросах, но не при простых вопросах типа «объясни что такое retention». Это особенно важно если скилл будет использоваться в Claude Code или MCP-окружении.
